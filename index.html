Framework Reference

Internal patterns and conventions — Bane Invoice Backend

This document is a framework-level reference for the backend conventions used across the project. It explains the shared patterns, request lifecycle, model behavior, logging conventions, and extension points that developers are expected to follow when building or modifying features. It is not a product specification or a feature catalog; it describes the operating model of the application rather than the business logic of any single module.

Middleware & Request Enrichment

Two middleware classes run on every request. Understanding what they attach to request is essential before reading the view/log sections.

RequestMiddleware

File: main/middleware.py. Runs first. Attaches context used everywhere.

AttributeTypeWhat it is
request._activity_id str (UUID) Fresh UUID for every request. All activity log entries generated during this request share this ID.
request.active_company Company | None Decoded from the JWT token's active_company claim. None if the token has no company claim or no token is present.
request._impersonated_by str | None Username of the admin acting on behalf of another user. Taken from JWT claim impersonated_by.
request._cached_body bytes Raw request body, cached so it can be read multiple times (middleware and views can both read it).

RequestResponseLoggingMiddleware

Runs after the response. For every non-health-check request:

  • Logs request and response to Celery (log_in_background).
  • On error responses (4xx/5xx) generates an error_id UUID, saves a failed-action activity log, and sends a Slack alert.
  • Auth endpoints (/api/auth/, token refresh, password reset) — logged on error as type=auth with changes={} (body stripped to avoid recording credentials).

get_current_request()

Thread-local accessor. Returns the current HTTP request from anywhere in the codebase — signals, helpers, services — without passing it explicitly through call chains.

from main.middleware import get_current_request

request = get_current_request()  # None outside an HTTP request context
Rule: use get_current_request() instead of threading the request through function arguments. If it returns None, you're in a background context — use system_actor for attribution.

ViewSets & Generic Views

All views extend the classes in utils/generic_views.py, which wrap DRF generics with consistent response building and automatic company scoping.

Class HTTP Methods Use when
ModelViewSet GET list · GET detail · POST · PATCH · DELETE Full CRUD resource with a router
ListCreateAPIView GET · POST Collection endpoint (no detail/update/delete)
ListAPIView GET Read-only list
RetrieveAPIView GET (single object) Read-only detail
CreateAPIView POST Create-only endpoint
UpdateAPIView PATCH Update-only endpoint
ListUpdateAPIView GET · PATCH List + partial update on a single URL

What these views do automatically

  • Return every response via build_response() in the standard envelope.
  • When WithinCompanyScope is present: filter list/retrieve/update/destroy to request.active_company, and inject company = request.active_company on create.
  • Validate query params through query_serializer and apply filters on list.
  • Activate pagination only when ?limit= is in the query string.
For anything outside these patterns — custom actions, complex multi-step logic — use a plain APIView and call build_response() manually.

ViewSet Variables

Variable Purpose & Notes

Complete Example

from utils.generic_views import ModelViewSet
from utils.permissions import WithinCompanyScope
from main.helper.paginationHelper import CustomPagination
from rest_framework import serializers

class FlightQuerySerializer(serializers.Serializer):
    status    = serializers.CharField(required=False)
    airline   = serializers.IntegerField(required=False)
    search    = serializers.CharField(required=False)
    date_from = serializers.DateField(required=False)

class FlightViewSet(ModelViewSet):
    object_name      = "Flight"
    queryset         = Flight.objects.all()
    serializer_class = FlightSerializer
    permission_classes = [WithinCompanyScope]
    pagination_class = CustomPagination
    query_serializer = FlightQuerySerializer
    tab_fields       = ["status"]  # excluded when counting tabs

    def advanced_filtering(self, queryset, query_serializer, ignore_fields=None):
        data = query_serializer.validated_data
        ignore = ignore_fields or []
        if data.get("status") and "status" not in ignore:
            queryset = queryset.filter(status=data["status"])
        if data.get("airline"):
            queryset = queryset.filter(airline_id=data["airline"])
        if data.get("search"):
            queryset = queryset.filter(flight_no__icontains=data["search"])
        if data.get("date_from"):
            queryset = queryset.filter(departure_date__gte=data["date_from"])
        return queryset

    def tab_count_data(self, queryset):
        return {
            "all":    queryset.count(),
            "active": queryset.filter(status="active").count(),
            "closed": queryset.filter(status="closed").count(),
        }

What this gives you for free:

  • List — company-scoped, paginated if ?limit= given, filtered by any query param, tab counts in response.
  • Create — company injected automatically from request.active_company.
  • Retrieve / Update / Destroy — company-scoped (can't access another company's objects).
  • All responses — consistent build_response envelope with object_name-based messages.

Filtering & Tabs

Basic filtering (no advanced_filtering)

When query_serializer is set but advanced_filtering is not, every validated field is applied directly as queryset.filter(**validated_data). Only use this when every field maps 1:1 to a model field with an exact match.

class InvoiceQuerySerializer(serializers.Serializer):
    payment_status = serializers.CharField(required=False)
    company        = serializers.IntegerField(required=False)
# GET /invoices/?payment_status=paid  →  .filter(payment_status="paid")

Advanced filtering

Use when you need non-exact matches, OR conditions, range filters, or annotations. The view calls advanced_filtering(queryset, query_serializer) instead of the auto-filter path.

def advanced_filtering(self, queryset, query_serializer, ignore_fields=None):
    data = query_serializer.validated_data
    ignore = ignore_fields or []

    # Tab field — skip when computing counts for other tabs
    if data.get("status") and "status" not in ignore:
        queryset = queryset.filter(status=data["status"])

    # Range filter
    if data.get("date_from"):
        queryset = queryset.filter(dep_date__gte=data["date_from"])
    if data.get("date_to"):
        queryset = queryset.filter(dep_date__lte=data["date_to"])

    # OR / icontains search
    if data.get("search"):
        queryset = queryset.filter(
            Q(flight_no__icontains=data["search"]) |
            Q(operator__name__icontains=data["search"])
        )
    return queryset

How tab counts work

When tab_count_data and tab_fields are both set, the framework calls:

# count queryset = advanced_filtering(base_qs, params, ignore_fields=tab_fields)
# The tab filter is stripped so counts show all tabs, not just the active one
tab_fields = ["status"]

def tab_count_data(self, queryset):   # queryset here has no status filter
    return {
        "all":    queryset.count(),
        "open":   queryset.filter(status="open").count(),
        "closed": queryset.filter(status="closed").count(),
    }

Tab counts appear in every list response — paginated or not — under data.tab_count_data.

Bare API Views

Use plain DRF APIView for custom actions, multi-step operations, or anything the generic views can't express. You are responsible for calling build_response().

from rest_framework.views import APIView
from rest_framework import status
from main.helper.responseHelper import build_response

class VoidInvoiceView(APIView):
    object_name = "Invoice"   # still required — exception handler uses it

    def post(self, request, pk):
        invoice = get_object_or_404(Invoice, pk=pk)
        if invoice.status == "voided":
            return build_response(
                "failed",
                error="Invoice is already voided",
                message="Invoice Failed To Void",
                status_code=status.HTTP_400_BAD_REQUEST,
            )
        invoice.void()
        return build_response(
            "success",
            data=InvoiceSerializer(invoice).data,
            message="Invoice Voided Successfully",
            status_code=status.HTTP_200_OK,
        )

Manual serializer validation in bare views

Generic views use serializer.is_valid(raise_exception=True) — the exception handler formats the errors automatically. Bare APIViews often call is_valid() without raising and handle errors manually. Use the parsers from main/helper/exceptionParser.py to format them for build_response.

FunctionInputOutputUse when
exception_list_parser serializer.errors.items() {"field": "first error message", ...} Serializer validation failed — convert DRF's nested error lists to a flat dict for errors=
exception_parser str(exception) {"field": "message"} or the raw string Caught an exception whose string representation looks like a Django ErrorDetail dict — tries to parse it, falls back to the raw string 
from main.helper.exceptionParser import exception_list_parser, exception_parser

class CreateFlightView(APIView):
    object_name = "Flight"

    def post(self, request):
        serializer = FlightSerializer(data=request.data)
        if not serializer.is_valid():
            return build_response(
                "failed",
                errors=exception_list_parser(serializer.errors.items()),
                message="Flight Failed To Create",
                status_code=status.HTTP_400_BAD_REQUEST,
            )
        try:
            instance = serializer.save()
        except Exception as e:
            return build_response(
                "failed",
                error=exception_parser(str(e)),   # parses ErrorDetail string if possible
                message="Flight Failed To Create",
                status_code=status.HTTP_400_BAD_REQUEST,
            )
        return build_response(
            "success",
            data=FlightSerializer(instance).data,
            message="Flight Successfully Created",
            status_code=status.HTTP_201_CREATED,
        )
If you use serializer.is_valid(raise_exception=True) instead, you don't need these parsers — the global exception handler calls format_error_details automatically and builds the response for you.

build_response

File: main/helper/responseHelper.py. The single function all views use to build HTTP responses. Never return a raw DRF Response() in a view.

from main.helper.responseHelper import build_response

build_response(
    status      = "success" | "failed",   # required
    message     = "...",                   # required
    status_code = status.HTTP_200_OK,       # required — DRF status constant
    data        = ...,                      # success only
    error       = ...,                      # failed only — single string/dict
    errors      = ...,                      # failed only — per-field dict
    tab_count_data = {},                    # optional — appended to data
    extra_data     = {},                    # optional — appended to data
)
ParameterWhenNotes
statusAlways"success" or "failed". Any other value raises an exception.
messageAlwaysHuman-readable. Shown to users in some contexts. Must be provided or the function throws.
status_codeAlwaysUse status.HTTP_* constants from DRF. Required or the function throws.
dataSuccessSerialized payload. Wrapped inside data.result in the response body.
errorFailedA single error — string or dict. Use for top-level, non-field errors (e.g. "Invoice already voided", gRPC failure, business rule violation).
errorsFailedPer-field validation errors from a serializer. Dict of { field: "message" }. The exception handler populates this automatically for 400s — you rarely set it manually.
tab_count_dataOptionalDict merged into data alongside result.
extra_dataOptionalArbitrary dict merged into data. Use for metadata alongside the main payload.
error vs errors: error = one thing went wrong. errors = multiple fields failed validation. If neither is passed on a failed response, the function raises an exception.

Success response

{
  "status": "success",
  "message": "Flight Successfully Fetched",
  "data": {
    "result": [ ... ],                // your serialized payload
    "tab_count_data": { "all": 42 }  // if tab_count_data was set
  }
}

Failed response — single error

{
  "status": "failed",
  "message": "Invoice Failed To Void",
  "error": "Invoice is already voided",
  "errors": null
}

Failed response — field validation errors

{
  "status": "failed",
  "message": "Flight Failed To Create",
  "error": null,
  "errors": {
    "dep_date": "This field is required.",
    "airline": "Please select a valid option."
  }
}

Class: CustomPagination in main/helper/paginationHelper.py.

Pagination is opt-in per request. Set pagination_class = CustomPagination on the view to enable it. It only activates when ?limit= is present — without it, the full queryset is returned as a flat list.

Exception Handler

Registered in REST_FRAMEWORK.EXCEPTION_HANDLER → main.middleware.custom_exception_handler.

All DRF exceptions are caught globally and transformed into the build_response envelope. Views do not need to catch or format these themselves.

StatusTriggered byResponse shape
400 Serializer raise_exception=True, or any DRF ValidationError Field errors: errors dict keyed by field name (via format_error_details which recursively flattens list-wrapped messages to strings).
Non-field / list error: error string.
Message: "{object_name} Failed To {Create|Update|Fetch|Delete}"
401 JWT token missing, expired, or invalid message: "Authentication Failed", error: token detail string
403 Permission class denied access message: "Access Denied", error: DRF detail string
404 get_object_or_404, or DRF NotFound error: "{object_name} Not Found", message: "{object_name} Failed To {method}"
503 raise GrpcServiceUnavailableError() error: "BAS service unavailable", message: service temporarily unavailable
format_error_details flattens nested serializer errors. DRF returns {"dep_date": ["This field is required."]} — the handler converts it to {"dep_date": "This field is required."}. Nested serializer errors are recursively flattened the same way.

What a 400 field-error response looks like

{
  "status": "failed",
  "message": "Flight Failed To Create",
  "error": null,
  "errors": {
    "dep_date": "This field is required.",
    "airline": "Please select a valid option."
  }
}

What a 400 non-field error looks like

{
  "status": "failed",
  "message": "Invoice Failed To Create",
  "error": "Flights from different companies cannot be on the same invoice.",
  "errors": null
}
object_name is required on every view, including plain APIView. The 400 and 404 handlers read view.object_name — if it's missing you get an AttributeError instead of a clean error response.

Soft Delete

File: utils/custom.py. Rows are never physically removed. Deletion sets deleted_at to the current time. The default manager hides deleted rows transparently.

ClassProvides
SoftDeletableModeldeleted_at field, two managers, overridden .delete()
TimeStampedModelcreated_at (immutable), updated_at (auto on update)
TimeStampedSoftDeletableModelBoth — use this as the base for most models

deleted_at sentinel value

Active rows use a far-future date as a sentinel instead of NULL. This allows indexing and prevents NULL comparison issues in MySQL.

Statedeleted_at value
Active3000-01-01 00:00:00 UTC — the FUTURE_DATE constant
DeletedActual timestamp of when .delete() was called

Managers

ManagerReturnsUse when
Model.objects Only rows where deleted_at = FUTURE_DATE All normal queries — this is the default
Model.all_objects All rows, including deleted Audit queries, admin, restoring deleted records

Deleting

# Soft delete (default) — sets deleted_at, fires post_save signal
instance.delete()

# Hard delete — physically removes the row, fires post_delete signal
instance.delete(soft=False)

# Access deleted items
Flight.all_objects.filter(deleted_at__lt=FUTURE_DATE)  # all deleted flights
Flight.all_objects.get(pk=42)                           # specific row, alive or dead
Queryset .delete() bypasses instance .delete(). Flight.objects.filter(...).delete() runs a bulk SQL UPDATE deleted_at = now(). It fires no pre_save / post_save signals. No activity logs are written. If you need an audit trail, iterate and call .delete() per instance, or log manually after the bulk update.

Timestamps

FieldBehaviour
created_at Set to timezone.now() on first save. Never changed thereafter.
updated_at null after the first save (create). Set to timezone.now() on every subsequent save. Check updated_at is None to know if a record has never been edited.

Company Settings

File: company/setting_keys.py. Per-company key/value configuration. All settings are seeded automatically when a new company is created.

How it works

  1. A new Company is saved → post_save fires populate_company_data_upon_company_creation.
  2. That signal calls seed_company_settings(company).
  3. seed_company_settings iterates get_default_settings() and runs CompanySettings.objects.get_or_create(title=key, company=company, defaults=...) for every entry.
  4. The company now has a CompanySettings row for every registered key, with its default value.

Adding a new setting

Two edits, both in company/setting_keys.py:

# 1. Add the key to the enum
class CompanySettingKey(str, Enum):
    ...
    MY_NEW_SETTING = "my_new_setting"

# 2. Add a default entry in get_default_settings()
def get_default_settings(company):
    return [
        ...
        {
            "title": CompanySettingKey.MY_NEW_SETTING,
            "defaults": {
                "value_type": CompanySettings.GeneralSettingsTypes.text.value,
                "type": CompanySettings.CompanySettingsTypes.general_settings.value,
                "value_text": "default_value",
            },
        },
    ]
Seeding is idempotent and also runs during startup. The app invokes python manage.py seeder company_settings on boot, and the company creation signal also calls seed_company_settings(company). Because it uses get_or_create, re-running it is safe and only fills in missing settings for each company.

Reading a setting

from company.setting_keys import CompanySettingKey, get_company_setting

setting = get_company_setting(company, CompanySettingKey.INVOICE_NUMBER_PREFIX)
if setting:
    prefix = setting.value_text   # e.g. "INV-"

get_company_setting returns a CompanySettings instance or None. Always guard against None — the setting may not exist for older companies that predate the key.

Changes Format

The changes JSON field records what changed in a save. The diff is computed by field_changes() in utils/signals.py.

Standard field diff

{
  "status": { "from": "open", "to": "closed" },
  "dep_date": { "from": "2026-10-01", "to": "2026-10-02" },
  "payable_amount": { "from": 1200.50, "to": 1350.00 }
}

FK field — includes human label

When a foreign key changes, the diff includes both the PK and the display label (if the related model has get_log_label()).

{

    "from": 3,                   // PK
    "to": 7,
    "from_label": "Emirates", // from get_log_label()

Every Flight log entry includes a plain string flight_status snapshot — the status of the flight at the time of the save, e.g. incomplete, ready_to_bill, billing, or billed.

Auto-logging Signals

Registered in InvoiceConfig.ready() for every model in the invoice app. The registration is automatic — no per-model setup needed.

SignalHandlerWhat it does
pre_save capture_model_changes Before the save hits the DB, loads the existing row from the DB and diffs it against the incoming instance. For new rows, records all fields as "from null". Stashes the result in instance._changes and instance._created.
post_save handle_model_changes Reads instance._changes. Decides action type: create, update, or delete (a soft-delete triggers update that gets re-classified as delete when deleted_at changed from FUTURE_DATE to now). Dispatches save_activity_log.delay() inside transaction.on_commit.
post_delete handle_model_delete Logs a hard delete. Only fires when .delete(soft=False) is used.
Logs are dispatched asynchronously via Celery inside transaction.on_commit — they never block the request and are only written after the DB commit succeeds. If the transaction rolls back, no log is written.

Bulk Operations — Manual Logging Required

Signals do not fire for bulk operations. queryset.update(), queryset.delete(), and queryset.bulk_create() bypass Django's signal machinery entirely. No activity logs are written for those operations, and you must handle any required side effects explicitly.

That applies to bulk data changes in general; for example, a bulk flight status update will not trigger the normal activity-log save path unless you log it yourself.

How to log a bulk operation

from django.db import transaction
from main.tasks import save_activity_log
from activityLog.models import ActivityLog

# Snapshot the pre-update state before the bulk write.
flight_ids = [42, 43, 44]
flights = Flight.objects.filter(id__in=flight_ids, company=request.active_company)
before = {flight.id: flight.status for flight in flights}

# Bulk update bypasses model-save signals.
Flight.objects.filter(id__in=flight_ids).update(status=Flight.FlightStatus.VOID)

# Emit one log per affected row, and only after the DB transaction commits.
for flight in flights:
   changes = {
       "status": {
           "from": before[flight.id],
           "to": Flight.FlightStatus.VOID.value,
       }
   }
   per_log = {
       "type": ActivityLog.ActionType.update,
       "model": "Flight",
       "object": flight.id,
       "changes": changes,
       "status": ActivityLog.ActionStatus.success,
       "user_name": request.user.username,
       "email": request.user.email,
       "company_id": request.active_company.id,
       "activity_id": request._activity_id,
   }
   transaction.on_commit(lambda d=per_log: save_activity_log.delay(**d))

System Actor

File: utils/actor_context.py.

When code runs outside an HTTP request (Celery tasks, management commands, background enrichments), there is no authenticated user. Without a declared actor, activity logs record an empty user_name. Use system_actor to attribute the logs to a named source.

When to use it

  • Management commands that modify data (enrichment sweeps, import scripts).
  • Celery tasks that save models directly (not triggered by a user request).
  • Any code path where get_current_request() would return None.

You do not need it for tasks dispatched from an HTTP request if you pass activity_id=request._activity_id — the request's user is resolved at dispatch time.

from utils.actor_context import system_actor, with_system_actor

# Context manager — wrap the block that saves models
with system_actor("FR24"):
    flight.enrich_from_fr24()   # any .save() inside logs as "System · FR24"

# Decorator — for management command handle() methods
@with_system_actor("FR24")
def handle(self, *args, **options):
    ...

# Nested actors compose into a readable chain
with system_actor("FR24"):        # outer: FR24 enrichment
    with system_actor("BAS"):    # inner: BAS fill called from within
        flight.save()             # logs as "System · FR24 · BAS"
Scenariouser_name in log
Authenticated HTTP requestUser's username
No request + system_actor("FR24")System · FR24
No request + no actor declaredSystem
Nested: FR24 → BASSystem · FR24 · BAS
The actor is stored in a thread-local stack. It's always cleaned up in a finally block, so it's safe on Celery workers where threads are reused across tasks.

Activity ID

Every HTTP request gets a UUID assigned by RequestMiddleware as request._activity_id. All activity log entries generated during that request share this ID. This lets you reconstruct the complete audit trail for any user action — even when it touches multiple models.

How to propagate it

ContextHow
HTTP request → log Automatic. Signal handlers read get_current_request()._activity_id.
HTTP request → Celery task Pass activity_id=request._activity_id to .delay(). ActivityTrackedTask picks it up and sets it into thread-local before the task runs.
Management command Extend ActivityTrackedCommand instead of BaseCommand. It generates a UUID for direct CLI invocations and inherits the caller's ID when called via call_command().
Standalone Celery task (no HTTP origin) Seeded automatically with the Celery task UUID by a task_prerun signal in utils/task_context.py. 
# Dispatching a task — pass activity_id so the task's logs group with this request
some_task.delay(
    invoice_id=invoice.id,
    activity_id=request._activity_id,
)

# Management command — activity_id handled automatically
from utils.management.base import ActivityTrackedCommand

class Command(ActivityTrackedCommand):
    def handle(self, *args, **options):
        # Any model saves here share the same activity_id
        ...

Log merging within a request

Within a single request (or task), multiple saves to the same model instance produce one log row, not many. save_activity_log looks up an existing (activity_id, model, object) row before inserting. If one exists, the changes are merged.

Merge rules:

  • The original "from" is preserved. Only "to" is updated to the latest value.
  • If a field returns to its original value (A → B → A), it is dropped from the diff — net-zero changes are invisible.
  • Without an activity_id, no merge happens — a new row is inserted every time.
This is why passing activity_id matters beyond its use as a query key. Without it, a request that saves the same object twice produces two log entries with partial diffs. With it, the log shows the final net change as a single row.

Celery Tasks

File: utils/task_context.py. Use ActivityTrackedTask as the base class for every Celery task. It propagates activity_id into thread-local before the task runs, so any model saves inside the task are attributed to the correct request or background job.

from celery import shared_task
from utils.task_context import ActivityTrackedTask

@shared_task(base=ActivityTrackedTask)
def process_invoice(invoice_id, activity_id=None):
    # activity_id is popped by ActivityTrackedTask before this runs
    # any model .save() inside here will carry the right activity_id
    ...
activity_id does not need to be in the function signature — ActivityTrackedTask.__call__ pops it from kwargs before invoking the function. Pass it at the call site: process_invoice.delay(invoice_id=42, activity_id=request._activity_id).

For standalone tasks with no HTTP origin, a task_prerun signal automatically seeds activity_id with the Celery task UUID, so logs are still grouped even without an explicit pass-through.

RPC Layer

When the app talks to an external service, keep the transport client behind a stable facade. Business code should depend on the facade, not the raw transport layer.

LayerRoleContract
Transport client Low-level RPC / gRPC / HTTP client Handles connection setup, serialization, and retry/error plumbing. Keep this thin and generic.
Facade / handler App-facing API Normalises responses into plain dicts / app types and centralises error handling.
Service call site Business logic Imports the facade only. Never reach into the raw transport client directly. 
# Correct
from rpc.remote_data_handler import get_client_by_id, get_aircraft_by_id

# Wrong — bypasses the facade and couples app code to transport details
from rpc.bas_rpc.grpc_client import BASService  # ✗

Keep a single error-handling path at the facade boundary. Translate transport exceptions into the app's normal error contract — whether that means returning None, raising a domain error, or converting a raw RPC error into a validation error.

Rule of thumb: the rest of the app should not know whether the external system is gRPC, HTTP, or REST. It only knows the facade contract.

Permissions

File: utils/permissions.py. Stack permissions in permission_classes — all must pass.

ExtendedDjangoModelPermissions

File: main/helper/customPermissionsHelper.py. Replaces DRF's default DjangoModelPermissions as the global permission class.

It keeps the standard Django-permission model, but adds stricter read access checks and a supporting-data fallback for read-only reference endpoints. In practice, the rule is: all permission checks are centralized in the custom class, and most view-level permission logic is declarative instead of ad hoc.

This is the default permission class set in REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES. Every view uses it unless permission_classes is overridden explicitly.

CustomBackend

File: main/helper/customPermissionsHelper.py. Custom Django authentication backend registered in AUTHENTICATION_BACKENDS.

Overrides _get_group_permissions to resolve group permissions through ExtendedGroup (via the extendedgroup__ relation) instead of Django's built-in Group. This means all permission checks (user.has_perm(), DjangoModelPermissions) work against ExtendedGroup memberships, not the default group system.

FK display labels in activity log

When a foreign key field changes, the diff records both the PK (from / to) and a human-readable label (from_label / to_label). The label comes from get_log_label() on the related model. Without it, str(instance) is used as a fallback.

class Airline(TimeStampedSoftDeletableModel):
    name = models.CharField(max_length=100)

    def get_log_label(self):
        return self.name   # → stored as "from_label" / "to_label" in changes
